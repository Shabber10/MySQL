# Day 09: Chapter 1 — Indexing for Search Optimization

As databases grow to millions of rows, searching for specific records using standard queries becomes increasingly slow. Without optimization, the database engine must inspect every single row in the table, a costly process known as a **Full Table Scan**. **Indexing** is the primary method used to speed up data retrieval.

---

## 1. What is an Index?

An **Index** is a separate, hidden data structure (typically a B-Tree) that the database builds to map column values directly to their physical locations in the table. 

### 📚 The Book Index Analogy
Imagine looking for a specific topic in a 1,000-page textbook:
*   **Without an Index:** You must flip through every page from page 1 to 1000 until you find it (Full Table Scan).
*   **With an Index:** You flip to the alphabetical index at the back, locate the term, read the page number, and jump directly to that page (Index Scan).

---

## 2. B-Tree Indexes (MySQL's Default)

In MySQL's default InnoDB engine, indexes are structured as balanced trees (**B-Trees**). 

```
                       [ Root Node ]
                           │ 25 │
                         ┌─┴────┴─┐
                        ▼        ▼
                 [ Leaf Node ]  [ Leaf Node ]
                 │ 10 │ 20 │    │ 30 │ 40 │
```

A B-Tree divides data into a tree hierarchy:
*   Instead of scanning rows linearly ($O(N)$ time), the engine traverses branches based on comparisons, reaching any record in logarithmic time ($O(\log N)$).
*   For a table containing **1,000,000 (1 million) rows**, a B-Tree search requires only about **3 to 4 lookups** to find a record.

---

## 3. Categories of Indexes

MySQL uses different types of indexes depending on the key constraints and column groupings:

### A. Clustered Index (Primary Index)
A **Clustered Index** determines the physical sorting order of rows on disk.
*   In MySQL InnoDB, the **Primary Key** automatically acts as the Clustered Index.
*   A table can have **only one** Clustered Index because data rows can only be physically sorted in one way.
*   Retrieval is extremely fast because reaching the index leaf node yields the actual data row directly.

### B. Secondary Index (Non-Clustered Index)
A **Secondary Index** is created on non-primary key columns.
*   Instead of storing the actual data row, secondary index leaf nodes store the column's indexed value along with a **pointer** to the corresponding Primary Key value.
*   When querying via a secondary index, the engine does a **two-step lookup** (first searches the secondary index to find the PK, then uses the PK to fetch the actual row).

### C. Unique Index
Enforces that all values in the indexed column are unique (automatically created by `UNIQUE` constraints).

### D. Composite Index (Multiple-Column Index)
An index built on two or more columns in a single definition.
*   *Example:* `CREATE INDEX idx_name ON Customers(last_name, first_name);`

#### 🔑 The Leftmost Prefix Rule
A composite index can only be utilized by queries that filter by the indexed columns in order from left to right:
- **`WHERE last_name = 'Smith'`**: Uses the index.
- **`WHERE last_name = 'Smith' AND first_name = 'John'`**: Uses the index.
- **`WHERE first_name = 'John'`**: **Cannot** use the index (violates leftmost prefix prefix rule; must scan table).

---

## 4. Index Lifecycle Commands

### A. Creating Indexes
*   **Standard Index:**
    ```sql
    CREATE INDEX idx_city ON Customers(city);
    ```
*   **Unique Index:**
    ```sql
    CREATE UNIQUE INDEX idx_email ON Customers(email);
    ```
*   **Composite Index:**
    ```sql
    CREATE INDEX idx_customer_location ON Customers(city, country);
    ```

### B. Viewing Active Indexes
To inspect what indexes exist on a table and their cardinality:
```sql
SHOW INDEX FROM Customers;
```

### C. Dropping Indexes
```sql
ALTER TABLE Customers DROP INDEX idx_city;
-- or
DROP INDEX idx_city ON Customers;
```

## ⚖️ When to Index (and When NOT to)

While indexes speed up read performance, they come with a cost: **every write operation (`INSERT`, `UPDATE`, `DELETE`) requires updating the B-Tree index, slowing down modifications.**

### ✔ When to Add an Index:
1.  Columns frequently referenced in `WHERE` clauses.
2.  Columns used to join tables (`ON` clauses).
3.  Columns used for sorting (`ORDER BY`) or grouping (`GROUP BY`).

### ❌ When to Avoid an Index:
1.  **Low Cardinality Columns:** Columns with very few unique values (e.g., `status` containing only 'Active'/'Inactive', or `gender`). The engine will choose a table scan anyway.
2.  **Frequently Updated Columns:** Tables with high write rates where update performance is critical.
3.  **Small Tables:** Tables with only a few hundred rows. A full table scan in memory is faster than traversing index structures.
