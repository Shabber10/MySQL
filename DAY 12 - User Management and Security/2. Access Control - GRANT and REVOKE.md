# Day 12: Chapter 2 — Access Control (GRANT and REVOKE)

Once a user is created, they cannot access any database or perform any operations by default. You must explicitly give them permissions. In SQL, this is called **Access Control** and is managed using the `GRANT` and `REVOKE` statements.

---

## 🔑 1. Understanding Privileges

Privileges define what operations a user can perform. MySQL supports two broad categories of privileges:

### A. Specific Privileges
These limit users to specific DML or DQL actions:
*   **`SELECT`**: Read data from tables/views.
*   **`INSERT`**: Add new records.
*   **`UPDATE`**: Modify existing records.
*   **`DELETE`**: Remove records.

### B. Administrative Privileges (ALL PRIVILEGES)
*   **`ALL PRIVILEGES`**: Grants full control over the database/table (including SELECT, INSERT, UPDATE, DELETE, and structural changes).
*   **`WITH GRANT OPTION`**: Allows the user to grant their own permissions to other users.

---

## 🛠️ 2. The `GRANT` Statement

Use `GRANT` to assign permissions to a user.

### Syntax:
```sql
GRANT privilege_type ON database_name.table_name TO 'username'@'hostname';
```

### Examples:

#### 1. Granting SELECT (Read-only) Privilege
```sql
GRANT SELECT ON college.student TO 'faculty'@'localhost';
-- faculty can run SELECT but not INSERT, UPDATE, or DELETE
```

#### 2. Granting SELECT and INSERT Privileges
```sql
GRANT SELECT, INSERT ON college.student TO 'faculty'@'localhost';
-- faculty can read and add new rows, but cannot modify/delete existing ones
```

#### 3. Granting Full Privileges (Admin) with Grant Option
```sql
GRANT ALL PRIVILEGES ON college.* TO 'admin'@'localhost' WITH GRANT OPTION;
-- admin can perform all operations on the college database
-- WITH GRANT OPTION allows admin to create users and delegate access to them
```

---

## ❌ 3. The `REVOKE` Statement

Use `REVOKE` to take away permissions from a user.

### Syntax:
```sql
REVOKE privilege_type ON database_name.table_name FROM 'username'@'hostname';
```

### Example:
```sql
REVOKE SELECT ON college.student FROM 'faculty'@'localhost';
-- Removes read access from faculty; they will now get an 'Access Denied' error
```

---

## 🎓 4. Case Study: Real-World College Permissions Flow

To understand privilege hierarchy, imagine a college department with three roles:

1.  **Root (Principal)**: The superuser. Has absolute power over the entire MySQL server.
2.  **Admin (HOD)**: Appointed by the Principal. Has full control over the department data (`college` database) and can manage permissions.
3.  **Faculty (Teacher)**: Hired by the HOD. Has limited access to see and use student data, but cannot see sensitive information (like phone numbers/addresses) or modify the base structures.

### Permissions Flow Diagram:

```text
+-----------------------+
|    Root (Principal)   |
+-----------------------+
            |
            | 1. CREATE USER 'admin'
            | 2. GRANT ALL PRIVILEGES ON college.* WITH GRANT OPTION
            v
+-----------------------+
|      Admin (HOD)      |
+-----------------------+
            |
            | 3. CREATE USER 'faculty'
            | 4. CREATE VIEW student_public (Safe view without sensitive data)
            | 5. GRANT SELECT ON student_public
            v
+-----------------------+
|   Faculty (Teacher)   |
+-----------------------+
            |
            | 6. SELECT * FROM student_public; (SUCCESS ✔)
            |    SELECT * FROM student;        (ACCESS DENIED ❌)
            v
+-------------------------------+
| Sees only safe student data   |
| (sid, name, course, marks)    |
+-------------------------------+

-- If the Admin decides to remove access:
Admin (HOD) runs: REVOKE SELECT ON student_public FROM 'faculty'@'localhost';
Faculty (Teacher) tries SELECT -> ❌ Access Denied
```

### Summary of Privilege Levels:

| Privilege / Action | Root (Principal) | Admin (HOD) | Faculty (Teacher) |
| :--- | :---: | :---: | :---: |
| **All System Config** | Yes | No | No |
| **Manage Databases** | Yes | Yes (Granted DBs) | No |
| **Create Users** | Yes | Yes (WITH GRANT) | No |
| **Read Sensitive Data** | Yes | Yes | No (Only safe views) |
| **Revoke Access** | Yes | Yes | No |
