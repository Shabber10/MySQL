# Day 01: Database Design and ER Diagrams

Before writing SQL code, database designers must plan how data will be structured. This guide covers how to analyze requirements, identify entities, draw E-R (Entity-Relationship) diagrams, and convert those diagrams into tables.

---

## 1. Analyzing Database Requirements

Before building a database, you must identify:
1.  What information needs to be stored.
2.  Who will be accessing and modifying the data.
3.  What the business rules are.

*Example:* If you are building a school database, you need to store student personal details, teacher contact info, subjects offered, exam marks, and student attendance.

---

## 2. Entities and Relationships

To represent real-world objects in a database, we use **Entities** and **Relationships**:

*   📌 **Entity:** A person, place, object, or event that we want to store data about.
    *   *Examples:* `Student`, `Teacher`, `Book`, `Course`, `Order`.
*   📌 **Relationship:** A connection or link between two entities.
    *   *Examples:*
        *   A student **belongs to** a class.
        *   A teacher **teaches** a subject.
        *   A customer **places** an order.

---

## 3. E-R (Entity-Relationship) Diagrams

An **E-R Diagram** is a visual map showing how entities are structured and related. It acts as a blueprint before you construct tables.

### Key E-R Diagram Shapes & Symbols:

| Shape / Symbol | Element Name | Description & Example |
| :---: | :--- | :--- |
| **Rectangle** ▭ | **Entity** | A real-world object or table (e.g., `Student`, `Course`). |
| **Oval** ◯ | **Simple Attribute** | A property or column of an entity (e.g., `Name`, `Age`). |
| **Oval with Underline** <u>**PK**</u> / 🔑 | **Key Attribute (Primary Key)** | **A unique attribute that identifies each record.** Represented by an oval containing **underlined text** (e.g., <u>`student_id`</u> or <u>`RollNo`</u>). |
| **Double Oval** 🞉 | **Multivalued Attribute** | An attribute that can hold multiple values for a single entity (e.g., `Phone_Numbers`, `Skills`). |
| **Dashed Oval** ◌ | **Derived Attribute** | An attribute calculated from another attribute (e.g., `Age` derived from `Date_of_Birth`). |
| **Branching Ovals** ◯—◯ | **Composite Attribute** | An attribute made of sub-components (e.g., `Address` split into `Street`, `City`, `Pincode`). |
| **Diamond** ◆ | **Relationship** | Defines how entities connect to each other (e.g., `enrolls in`, `teaches`). |
| **Double Rectangle** ⧉ | **Weak Entity** | An entity that cannot be uniquely identified by its own attributes alone and depends on a owner entity. |

### Visual Layout Example:

```
        (Age) [Derived]
          ┆
   ┌──────────────┐                  ◆                  ┌──────────────┐
   │   STUDENT    │─────────────(Enrolls In)────────────│    COURSE    │
   └──────────────┘                                     └──────────────┘
     │        │                                                │
 <u>(RollNo)</u>   (Name)                                        <u>(CourseID)</u>
   [PK]                                                      [PK]
```
> 📌 **Key Rule:** In E-R Diagrams, every Primary Key attribute is drawn inside an **Oval with an Underline** beneath the attribute name (e.g., <u>`RollNo`</u> or <u>`student_id`</u>).


---

## 4. Converting E-R Diagrams to Tables

Once the visual design is complete, we translate the shapes into physical SQL tables.

### The Conversion Rules:
1.  **Rectangles (Entities)** become **Tables**.
2.  **Ovals (Attributes)** become **Columns** in those tables.
3.  **Relationships** are established by using **Primary Keys** and **Foreign Keys** to connect the tables.

### Example Conversion:
If we have a relationship where **Students** enroll in a **Class**:

**Student Table**
| StudentID (Primary Key) | Name | ClassID (Foreign Key) |
| :--- | :--- | :--- |
| 101 | Rahul | A-10 |
| 102 | Priya | B-20 |

**Class Table**
| ClassID (Primary Key) | ClassName |
| :--- | :--- |
| A-10 | Grade 10 |
| B-20 | Grade 11 |

Here, the `ClassID` column inside the **Student Table** is a **Foreign Key** pointing to the `ClassID` of the **Class Table**, establishing the link.
