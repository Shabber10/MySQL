# Day 13: Chapter 2 — Understanding EXPLAIN Query Plans

The **`EXPLAIN`** statement is the single most important tool in MySQL for query optimization. Prefixing any `SELECT`, `UPDATE`, or `DELETE` statement with `EXPLAIN` causes MySQL to return the **Execution Plan**—showing how the query optimizer intends to join tables, which indexes it evaluated, which index it selected, and how many rows it expects to scan.

---

## 🔍 Anatomy of an `EXPLAIN` Result

```sql
EXPLAIN SELECT o.order_id, c.name 
FROM Customers c 
JOIN Orders o ON c.customer_id = o.customer_id 
WHERE c.city = 'Delhi';
```

### Key Output Columns Explained:

| Column | Meaning | What to Look For |
| :--- | :--- | :--- |
| **`select_type`** | Type of SELECT query (`SIMPLE`, `PRIMARY`, `SUBQUERY`, `DERIVED`, `UNION`). | `SIMPLE` is best; nested `DERIVED` or `SUBQUERY` may indicate optimization opportunities. |
| **`table`** | The table to which the output row refers. | Watch the order of tables—MySQL joins tables in top-to-bottom order. |
| **`type`** | The **Join Type** (access mechanism used to find rows). | **Crucial indicator!** Ranges from fastest (`const`) to slowest (`ALL`). |
| **`possible_keys`** | List of indexes MySQL *could* use. | If `NULL`, no relevant indexes exist for the query filters. |
| **`key`** | The actual index MySQL **chose** to use. | If `NULL`, MySQL performed a full table scan. |
| **`key_len`** | The length of the chosen key in bytes. | Helps determine how many parts of a composite index are active. |
| **`rows`** | Estimated number of rows MySQL must examine. | **Lower is better!** Millions of rows indicates missing indexes. |
| **`filtered`** | Percentage of examined rows filtered by table conditions. | 100.00% is ideal. Low percentages (e.g. 10%) indicate late filtering. |
| **`Extra`** | Additional execution details (`Using index`, `Using filesort`, `Using temporary`). | Warning indicators for memory/disk overheads. |

---

## 📊 The Join Type (`type`) Hierarchy

The `type` column is the most critical metric in an `EXPLAIN` report. Aim to move your queries up the hierarchy:

```
    [ FASTEST / BEST ]
    ├── 1. system        : Table has only 1 row (system table).
    ├── 2. const         : Primary Key or Unique Index lookup with constant value (`WHERE id = 1`).
    ├── 3. eq_ref        : 1-to-1 Join lookup using Primary Key / Unique Index.
    ├── 4. ref           : Non-unique Index lookup (`WHERE city = 'Delhi'`).
    ├── 5. range         : Index Range scan using `<`, `>`, `BETWEEN`, `IN`, `LIKE 'abc%'`.
    ├── 6. index         : Full Index scan (scans entire index tree; faster than ALL).
    └── 7. ALL           : Full Table Scan (scans entire table from disk). ❌ AVOID IN PROD!
    [ SLOWEST / WORST ]
```

---

## 🚩 Decoding the `Extra` Column Warnings

The `Extra` column contains vital performance flags:

### 1. `Using index` (Covering Index ✅)
* **Meaning:** The query was answered **entirely from the index tree** without needing to read the actual table rows from disk.
* **Status:** Excellent performance!

### 2. `Using where` ✅
* **Meaning:** MySQL uses a `WHERE` clause to filter rows after reading them.

### 3. `Using filesort` ⚠️
* **Meaning:** MySQL must perform an extra sorting pass to order the results (because no suitable index exists for `ORDER BY`).
* **Fix:** Add a composite index covering both the `WHERE` filter and `ORDER BY` columns.

### 4. `Using temporary` 🚨
* **Meaning:** MySQL had to build an internal in-memory or disk-based temporary table to evaluate the query (common with `GROUP BY` or `DISTINCT` on non-indexed columns).
* **Fix:** Index the columns used in `GROUP BY`.

## ⚡ `EXPLAIN ANALYZE` (MySQL 8.0+)

While standard `EXPLAIN` displays **estimates**, `EXPLAIN ANALYZE` actually **executes the query**, measuring exact time spent in each execution node:

```sql
EXPLAIN ANALYZE 
SELECT c.city, COUNT(*) 
FROM Customers c 
JOIN Orders o ON c.customer_id = o.customer_id 
GROUP BY c.city;
```

### Sample Output:
```text
-> Table scan on c  (cost=0.75 rows=5) (actual time=0.035..0.045 rows=5 loops=1)
-> Hash join (c.customer_id = o.customer_id)  (cost=2.75 rows=5) (actual time=0.080..0.095 rows=4 loops=1)
```
* Shows actual start/end execution time in milliseconds and real row counts returned.
