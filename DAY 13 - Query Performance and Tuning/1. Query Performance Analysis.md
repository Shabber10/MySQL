# Day 13: Chapter 1 — Query Performance Analysis

As database tables scale from thousands to millions of rows, poorly written SQL queries can severely degrade application performance, leading to high CPU usage, slow response times, and server crashes. **Query Performance Analysis** is the process of identifying, diagnosing, and optimizing slow-running SQL statements.

---

## 🐢 1. Identifying Slow Queries: The Slow Query Log

MySQL provides a built-in diagnostic tool called the **Slow Query Log** to automatically record queries that exceed a specified execution time threshold.

### Enabling the Slow Query Log:
```sql
-- Enable slow query logging
SET GLOBAL slow_query_log = 'ON';

-- Set threshold (record queries taking longer than 2 seconds)
SET GLOBAL long_query_time = 2.0;

-- Optionally log queries that do not use indexes
SET GLOBAL log_queries_not_using_indexes = 'ON';
```

### Viewing Slow Query Status:
```sql
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';
```

---

## ⏱️ 2. Microsecond Benchmarking: MySQL Query Profiling

Query Profiling measures the exact execution time spent in each internal engine state (e.g., *sending data*, *sorting*, *opening tables*, *locking*).

### Running a Profile:
```sql
-- 1. Enable profiling for the current session
SET profiling = 1;

-- 2. Execute candidate queries
SELECT * FROM Orders WHERE YEAR(order_date) = 2026;

-- 3. View list of executed profiles
SHOW PROFILES;

-- 4. View detailed execution breakdown for query #1
SHOW PROFILE FOR QUERY 1;
```

## 🚨 Common Query Performance Anti-Patterns & Fixes

### ❌ Anti-Pattern 1: Wrapping Indexed Columns in Functions
When you wrap an indexed column in a function (such as `YEAR()`, `DATE()`, `SUBSTRING()`, or `LOWER()`), MySQL **cannot use the B-Tree index** because the function must be evaluated for every row. This forces a **Full Table Scan**.

* ❌ **Slow (Full Table Scan):**
  ```sql
  SELECT * FROM Orders WHERE YEAR(order_date) = 2026;
  ```
* ✅ **Fast (Uses Index Range Scan):**
  ```sql
  SELECT * FROM Orders WHERE order_date >= '2026-01-01 00:00:00' AND order_date <= '2026-12-31 23:59:59';
  ```

---

### ❌ Anti-Pattern 2: Overusing `SELECT *`
Selecting all columns transfers unnecessary data across the network, increases memory usage, and prevents MySQL from utilizing **Covering Indexes**.

* ❌ **Slow:**
  ```sql
  SELECT * FROM Orders WHERE customer_id = 101;
  ```
* ✅ **Fast:**
  ```sql
  SELECT order_id, order_date, amount FROM Orders WHERE customer_id = 101;
  ```

---

### ❌ Anti-Pattern 3: Implicit Data Type Conversion
If a column is defined as `VARCHAR` but you query it using an integer (or vice versa), MySQL implicitly converts the data type for every row, disabling the index.

* ❌ **Slow (Phone is VARCHAR):**
  ```sql
  SELECT * FROM Users WHERE phone = 9999911111; -- Numeric input forces implicit conversion!
  ```
* ✅ **Fast:**
  ```sql
  SELECT * FROM Users WHERE phone = '9999911111'; -- String literal matches column data type
  ```

---

### ❌ Anti-Pattern 4: Leading Wildcards in `LIKE` Queries
Indexes cannot be used when a search pattern starts with a wildcard (`%`).

* ❌ **Slow (Full Table Scan):**
  ```sql
  SELECT * FROM Customers WHERE email LIKE '%@gmail.com';
  ```
* ✅ **Fast (Index Range Scan):**
  ```sql
  SELECT * FROM Customers WHERE email LIKE 'rahul%';
  ```
