# Day 10/11: Chapter 1 — Automation with Triggers

A **Database Trigger** is a named, event-driven database object that is automatically executed (or "fired") whenever a specific Data Manipulation Language (DML) event—`INSERT`, `UPDATE`, or `DELETE`—occurs on a designated table.

Triggers are used to enforce complex integrity rules, maintain audit trails, automatically update aggregate tables, and prevent invalid data entry directly at the database layer.

---

## ⏰ Trigger Timing and Event Types

A trigger is defined by two key factors:
1. **Trigger Timing**: Specifies *when* the trigger executes relative to the table operation:
   * **`BEFORE`**: Fires *prior* to modifying the row in the database. (Ideal for data validation, scrubbing, or assigning default values).
   * **`AFTER`**: Fires *immediately after* the row modification is written to disk. (Ideal for audit logging, updating related tables, or sending notifications).
2. **Trigger Event**: The DML action that fires the trigger: `INSERT`, `UPDATE`, or `DELETE`.

### The 6 Trigger Combinations:
| Timing | Event | Typical Use Case |
| :--- | :--- | :--- |
| **`BEFORE INSERT`** | `INSERT` | Validating inputs, auto-formatting strings (e.g. UPPERCASE email), checking limits. |
| **`AFTER INSERT`** | `INSERT` | Writing audit records to an `AuditLog` table, decrementing inventory stock counts. |
| **`BEFORE UPDATE`** | `UPDATE` | Recording `last_modified` timestamps, validating new values against old values. |
| **`AFTER UPDATE`** | `UPDATE` | Logging changed columns into a history log table. |
| **`BEFORE DELETE`** | `DELETE` | Archiving rows to a `DeletedRecords` table, preventing deletion of critical rows. |
| **`AFTER DELETE`** | `DELETE` | Recalculating summary counts or clearing related cached counters. |

---

## 🔄 Pseudo-Row References: `OLD` and `NEW`

Inside a trigger body, MySQL provides access to the rows being modified through two pseudo-record qualifiers: `OLD` and `NEW`.

```
        INSERT Operation              UPDATE Operation              DELETE Operation
     ┌────────────────────┐        ┌────────────────────┐        ┌────────────────────┐
     │  OLD : (N/A)       │        │  OLD : Original    │        │  OLD : Deleted     │
     │  NEW : Incoming    │        │  NEW : Updated     │        │  NEW : (N/A)       │
     └────────────────────┘        └────────────────────┘        └────────────────────┘
```

### `OLD` and `NEW` Availability Matrix:
| Trigger Event | `OLD.column_name` | `NEW.column_name` | Explanation |
| :--- | :--- | :--- | :--- |
| **`INSERT`** | ❌ Unavailable (`NULL`) | ✅ **Available** | Represents the new row being inserted. (`NEW.col` can be modified in `BEFORE INSERT`). |
| **`UPDATE`** | ✅ **Available** | ✅ **Available** | `OLD.col` holds the pre-update value; `NEW.col` holds the proposed new value. |
| **`DELETE`** | ✅ **Available** | ❌ Unavailable (`NULL`) | `OLD.col` holds the data of the row being deleted. Read-only. |

## 🛠️ Trigger Syntax

```sql
DELIMITER //

CREATE TRIGGER trigger_name
{BEFORE | AFTER} {INSERT | UPDATE | DELETE}
ON table_name
FOR EACH ROW
BEGIN
    -- Trigger execution statements
    -- Use NEW.column_name or OLD.column_name
END //

DELIMITER ;
```
> **Note:** `FOR EACH ROW` means the trigger is a **row-level trigger**—if an `UPDATE` statement modifies 10 rows, the trigger executes 10 times (once for each row).

## 💡 Real-World Examples

### Example 1: `AFTER INSERT` Trigger (Automated Inventory Reduction & Audit Log)

Suppose whenever a customer places an order in `Orders`, we want to automatically subtract the ordered quantity from `Products.stock_quantity` and record the action in `AuditLog`.

```sql
DELIMITER //

CREATE TRIGGER after_order_placed
AFTER INSERT ON Orders
FOR EACH ROW
BEGIN
    -- 1. Deduct stock from Products table using NEW.product_id and NEW.quantity
    UPDATE Products
    SET stock_quantity = stock_quantity - NEW.quantity
    WHERE product_id = NEW.product_id;

    -- 2. Insert record into AuditLog
    INSERT INTO AuditLog (log_message)
    VALUES (CONCAT('Order #', NEW.order_id, ' placed for Product #', NEW.product_id, ' (Qty: ', NEW.quantity, ')'));
END //

DELIMITER ;
```

---

### Example 2: `BEFORE UPDATE` Trigger (Data Scrubbing & Timestamps)

Automatically update the `last_modified` column to the current timestamp and ensure the email address is stored in lowercase.

```sql
DELIMITER //

CREATE TRIGGER before_user_update
BEFORE UPDATE ON Users
FOR EACH ROW
BEGIN
    -- Scrub email input
    SET NEW.email = LOWER(NEW.email);
    
    -- Auto-assign modification timestamp
    SET NEW.last_modified = NOW();
END //

DELIMITER ;
```

---

### Example 3: Enforcing Business Rules with `SIGNAL SQLSTATE` (Validation Exception)

If an application attempts to insert a product with a negative price or insufficient stock, a `BEFORE` trigger can abort the transaction and raise a custom error using `SIGNAL SQLSTATE`.

```sql
DELIMITER //

CREATE TRIGGER before_order_validate
BEFORE INSERT ON Orders
FOR EACH ROW
BEGIN
    DECLARE available_stock INT;
    
    -- Check available stock
    SELECT stock_quantity INTO available_stock
    FROM Products
    WHERE product_id = NEW.product_id;
    
    -- If stock is insufficient, cancel insertion with custom error
    IF available_stock < NEW.quantity THEN
        SIGNAL SQLSTATE '45000'
        SET MESSAGE_TEXT = 'Error: Order cancelled. Insufficient inventory stock!';
    END IF;
END //

DELIMITER ;
```

## 📝 Managing Triggers

### A. Listing Triggers in a Database
```sql
SHOW TRIGGERS FROM day11_practice;
```

### B. Dropping a Trigger
```sql
DROP TRIGGER IF EXISTS after_order_placed;
```

> ⚠️ **Best Practice Warning:** Keep trigger logic fast and lightweight! Avoid long-running calculations or heavy loops inside triggers, as they run synchronously inside the transaction of the main statement and can slow down core application throughput.
