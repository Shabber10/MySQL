# Day 09: Chapter 2 — Creating and Using Views

A **View** is a virtual table whose contents are defined by a query. Unlike a standard table, a view does not store data physically on disk. Instead, the database stores the view's query definition. When you query a view, the database engine executes the underlying query on the fly to return the current data.

---

## 1. Why Use Views? (Benefits)

Views are highly valued in database architecture for three reasons:

### A. Security (Access Control)
Views allow you to restrict the columns or rows a user can see.
*   *Column-level:* Hide sensitive data. For example, you can create a view of the `Employees` table that excludes the `salary` and `national_id` columns.
*   *Row-level:* Restrict records. You can create a view showing only employees belonging to the 'HR' department.

### B. Simplicity (Query Encapsulation)
If your application frequently runs complex queries with multi-table joins, aggregations, or subqueries, you can encapsulate that logic into a view. The application can then query the view using simple statements.
*   Instead of writing a 10-line join query every time, you can run: `SELECT * FROM v_order_summaries;`.

### C. Consistency (Logical Data Independence)
If you rename columns or restructure tables in the database, you can update the view's query definition to match the new schema. External applications querying the view will continue working without any code modifications.

---

## 2. Creating and Querying Views

### Basic Syntax
```sql
CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;
```

Once created, you can query a view exactly like a normal table:
```sql
SELECT * FROM view_name WHERE column1 > 100;
```

---

## 3. Simple vs. Complex Views

### A. Simple Views
*   Reference only a **single base table**.
*   Do not contain groupings (`GROUP BY`), distincts (`DISTINCT`), joins, or aggregate functions.
*   **Updatable**: You can run `INSERT`, `UPDATE`, and `DELETE` queries on a simple view, and the changes are immediately passed down to modify the underlying base table.

### B. Complex Views
*   Reference **multiple tables** (using joins) or contain calculations, aggregates (`SUM`, `AVG`), or grouping.
*   **Read-Only**: In practice, you cannot perform write operations (inserts/deletes) through a complex view because the database cannot determine how to map the changes back to the multiple base tables.

---

## 4. Updatable Views & `WITH CHECK OPTION`

When updating data through a view, you must be careful not to "lose" the record you just inserted or updated. 

### The Problem (Without Check Option)
Consider this view:
```sql
CREATE VIEW v_delhi_staff AS
SELECT emp_id, name, city
FROM StaffDetails
WHERE city = 'Delhi';
```
If you insert a record through this view with a different city:
```sql
INSERT INTO v_delhi_staff (emp_id, name, city) VALUES (10, 'Rohan', 'Mumbai');
```
*   This statement succeeds and inserts Rohan into the underlying `StaffDetails` table.
*   However, because Rohan's city is 'Mumbai', he does not satisfy the view's filter (`WHERE city = 'Delhi'`). If you select from `v_delhi_staff`, Rohan is invisible! He has vanished from the view.

---

### The Solution: `WITH CHECK OPTION`
The `WITH CHECK OPTION` clause prevents inserts or updates through the view that do not satisfy the view's `WHERE` filter.

```sql
CREATE VIEW v_delhi_staff AS
SELECT emp_id, name, city
FROM StaffDetails
WHERE city = 'Delhi'
WITH CHECK OPTION;
```

Now, attempting to insert Rohan with 'Mumbai' will fail:
```sql
INSERT INTO v_delhi_staff (emp_id, name, city) VALUES (10, 'Rohan', 'Mumbai');
-- ❌ Throws Error:
-- ERROR 1369 (HY000): CHECK OPTION failed 'day9_practice.v_delhi_staff'
```

---

## 5. Altering & Dropping Views

### A. Replacing a View
To modify a view's query definition, use `CREATE OR REPLACE VIEW`:
```sql
CREATE OR REPLACE VIEW v_delhi_staff AS
SELECT emp_id, name, email, city
FROM StaffDetails
WHERE city = 'Delhi'
WITH CHECK OPTION;
```

### B. Dropping a View
To delete a view, use `DROP VIEW`:
```sql
DROP VIEW v_delhi_staff;
```
*(Note: Dropping a view only deletes the virtual table definition. The underlying base tables and their data remain completely untouched).*
