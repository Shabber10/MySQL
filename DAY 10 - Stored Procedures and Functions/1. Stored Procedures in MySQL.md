# Day 10: Chapter 1 — Stored Procedures in MySQL

A **Stored Procedure** is a set of SQL statements that are compiled and saved directly inside the database server. Once created, you can execute (or "call") the procedure whenever needed by name, passing input parameters and receiving output parameters.

Think of a Stored Procedure as a **mini-program running inside the database** (similar to functions in Java or Python, but executing natively on the database server).

---

## 1. Why Use Stored Procedures? (Advantages)

Stored procedures offer major architectural and security advantages in enterprise applications:

### 1️⃣ Reusability (Write Once, Call Anywhere)
Instead of re-writing complex SQL queries across multiple backend microservices, you write the procedure once in MySQL and call it from any application language (Node.js, Python, Java, PHP):
```sql
CALL GetHighSalaryEmployees(50000);
```

### 2️⃣ Better Performance (Reduced Network Traffic)
* **Without Stored Procedures:** An application sends 5 separate SQL queries over the network, waiting for the database response after each one.
* **With Stored Procedures:** The application sends a single `CALL` command over the network. All 5 queries execute internally on the database server, returning only the final result.

### 3️⃣ Security & Data Encapsulation
You can restrict direct table access from database users. Users do not need `SELECT`, `INSERT`, or `UPDATE` privileges on underlying tables—they only need `EXECUTE` permission on specific stored procedures:
```sql
GRANT EXECUTE ON PROCEDURE ProcessPayroll TO 'hr_user'@'localhost';
```
* **Result:** `hr_user` can run payroll logic without ever seeing or directly modifying raw `Employees` or `Salary` tables!

### 4️⃣ Centralized Maintainability
If business rules change (e.g., tax deduction rate updates from 10% to 12%), you update the logic in **one place** (the database procedure). All connected applications automatically get the new logic without needing application redeployments.

### 5️⃣ Transaction & Batch Operations
You can bundle multiple `INSERT`, `UPDATE`, and `DELETE` queries together with error handling and transaction controls (`START TRANSACTION`, `COMMIT`, `ROLLBACK`) inside a single procedure.

---

## ❌ Disadvantages of Stored Procedures

While powerful, stored procedures have tradeoffs:
1. **DB Server Resource Consumption:** Complex calculations utilize CPU and RAM on the database server rather than offloading work to application servers.
2. **Harder to Debug:** Lacks advanced debugging tools compared to modern application IDEs.
3. **Vendor Lock-in:** Stored procedure syntax varies between database vendors (MySQL vs Oracle PL/SQL vs SQL Server T-SQL), making database migration more difficult.

---

## 🆚 Stored Procedure vs. Database View

| Feature | View | Stored Procedure |
| :--- | :--- | :--- |
| **What is it?** | A saved `SELECT` query (a virtual table/display window). | A mini-program with full procedural logic. |
| **Supported Operations** | Reads data (`SELECT`). Simple views allow limited updates. | Can execute `INSERT`, `UPDATE`, `DELETE`, `SELECT`, and control flow (`IF`, `WHILE`). |
| **Parameters** | Does **NOT** accept input/output parameters. | Supports `IN`, `OUT`, and `INOUT` parameters. |
| **Usage** | Used in `FROM` clauses like a table (`SELECT * FROM my_view`). | Executed using the `CALL` statement (`CALL my_proc()`). |

## 🛠️ Understanding Delimiters (`DELIMITER //`)

By default, MySQL uses the semicolon (`;`) as the **statement delimiter** to signal the end of a command.

### The Problem inside Stored Procedures:
A stored procedure contains multiple SQL statements inside a `BEGIN ... END` block, and each statement ends with a `;`:
```sql
-- ❌ This causes a syntax error if run without changing the delimiter!
CREATE PROCEDURE InsertCustomer()
BEGIN
    INSERT INTO Customers VALUES (1, 'Rahul', 'Delhi'); -- MySQL sees ';' and thinks the query ends here!
    SELECT * FROM Customers;
END;
```
MySQL encounters the first `;` after the `INSERT` statement and assumes the entire `CREATE PROCEDURE` statement has ended, resulting in a broken, incomplete procedure error.

### The Solution:
We temporarily change the delimiter to a different symbol (such as `//` or `$$`) using the `DELIMITER` command:

```sql
-- Step 1: Change delimiter to //
DELIMITER //

CREATE PROCEDURE InsertCustomer()
BEGIN
    INSERT INTO Customers VALUES (1, 'Rahul', 'Delhi');
    SELECT * FROM Customers;
END // -- Step 2: Signal the end of the entire procedure definition with //

-- Step 3: Change delimiter back to standard semicolon
DELIMITER ;
```

## 📥 Parameter Modes: `IN`, `OUT`, and `INOUT`

Stored procedures accept three types of parameters:

```
               ┌──────────────────────────────────────────┐
               │          STORED PROCEDURE                │
               │                                          │
    IN ───────>│ Takes input value from caller            │
               │                                          │
   OUT ────────┼─────────────────────────────────────────>│ Returns output value to caller
               │                                          │
 INOUT <──────>│ Receives input value, modifies it,       │<──────>
               │ and returns updated value                │
               └──────────────────────────────────────────┘
```

### A. `IN` Parameters (Input Only)
Passes a value from the caller into the procedure. The procedure can read and use the value, but cannot modify the caller's original variable. (This is the default mode).

```sql
DELIMITER //

CREATE PROCEDURE GetEmployeesByDept(IN p_dept VARCHAR(50))
BEGIN
    SELECT * FROM Employees WHERE dept = p_dept;
END //

DELIMITER ;

-- Calling the procedure:
CALL GetEmployeesByDept('IT');
```

---

### B. `OUT` Parameters (Output Only)
Used to pass a value back from the procedure to the caller. Initial input value is ignored (`NULL`).

```sql
DELIMITER //

CREATE PROCEDURE GetEmployeeCount(OUT total_count INT)
BEGIN
    SELECT COUNT(*) INTO total_count FROM Employees;
END //

DELIMITER ;

-- Calling the procedure using a session variable (@count):
CALL GetEmployeeCount(@count);

-- Display the output variable value:
SELECT @count AS total_employees;
```

---

### C. `INOUT` Parameters (Input & Output)
Passes an initial value into the procedure, allows the procedure to modify it, and returns the modified value back to the caller.

```sql
DELIMITER //

CREATE PROCEDURE ApplySalaryIncrement(INOUT p_salary DECIMAL(10,2), IN p_percent DECIMAL(5,2))
BEGIN
    SET p_salary = p_salary + (p_salary * (p_percent / 100));
END //

DELIMITER ;

-- Calling the procedure:
SET @current_sal = 50000.00;
CALL ApplySalaryIncrement(@current_sal, 10.00); -- Apply 10% increment

-- Display updated salary:
SELECT @current_sal AS incremented_salary; -- Output: 55000.00
```

## 📝 Managing Stored Procedures

DROP PROCEDURE IF EXISTS GetEmployeesByDept;
