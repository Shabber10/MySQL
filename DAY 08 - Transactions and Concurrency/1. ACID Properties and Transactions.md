# Day 08: Chapter 1 — ACID Properties & Transactions

In relational database systems, multiple SQL operations must often execute as a single, indivisible unit of work. This logical container is called a **Transaction**. If even one operation within the transaction fails, all preceding changes must be reversed, leaving the database in its original state.

---

## 🏦 The Bank Transfer Scenario

To understand why transactions are critical, consider a bank transfer where Customer A sends $500 to Customer B:

1.  **Step 1:** Verify A's account has at least $500.
2.  **Step 2:** Subtract $500 from A's balance (Debit).
3.  **Step 3:** Add $500 to B's balance (Credit).

```
         Debit $500                     Credit $500
   ┌────────────────────┐   =======>   ┌────────────────────┐
   │     Account A      │   (Failure   │     Account B      │
   │  Balance: $1000-500│   Point!)    │   Balance: $200+500│
   └────────────────────┘              └────────────────────┘
```

*   **What if the system crashes after Step 2 but before Step 3?** 
    Without transactions, Customer A loses $500, but Customer B never receives it. The money vanishes.
*   **With Transactions:** Steps 2 and 3 are bound together. If a crash or failure occurs before Step 3 completes, Step 2 is rolled back, restoring Customer A's $500.

---

## 🔒 The ACID Properties

To guarantee database reliability, every transaction must satisfy the four **ACID** properties:

### 1. Atomicity ("All or Nothing")
A transaction is treated as a single, indivisible unit. Either **all** operations succeed and are committed, or **all** operations fail and are completely rolled back. There is no partial state.
*   *Implementation:* Enforced by the database logging system (Undo Log).

### 2. Consistency (Preserving Rules)
A transaction must transition the database from one valid state to another, maintaining all schema constraints, indexes, triggers, and business integrity rules.
*   *Example:* If a column has a CHECK constraint ensuring `balance >= 0`, a transaction that attempts to debit an account into a negative balance will violate consistency, causing the database to abort the transaction and roll it back.

### 3. Isolation (Independent Execution)
Concurrent transactions must execute independently without interfering with one another. The uncommitted, intermediate state of a transaction must remain invisible to other concurrent transactions.
*   *Why?* If Transaction A modifies a row and Transaction B reads it before Transaction A commits or rolls back, Transaction B makes decisions based on temporary, invalid data.

### 4. Durability (Permanence)
Once a transaction is committed, its changes are written to non-volatile storage (disk) and are guaranteed to survive any subsequent system crash or power outage.
*   *Implementation:* Enforced by transaction logs (Redo Log) written to disk before the database officially reports the commit as completed.

---

## 📑 Transaction Logs in MySQL: Redo Log & Undo Log

MySQL guarantees transaction safety through two internal low-level log systems in the InnoDB storage engine:

| Log Type | Purpose | ACID Property Enforced | Real-World Role |
| :--- | :--- | :--- | :--- |
| **Undo Log** | Stores the "before image" (original data before modification). | **Atomicity** & **Isolation** | Reverts changes if `ROLLBACK` is executed or system crashes mid-transaction. |
| **Redo Log** | Stores pending changes in memory before writing to disk. | **Durability** | Re-applies committed changes during crash recovery on server restart. |

### 📓 The "Backup Notebook" Analogy for Redo Logs
Think of the Redo Log as a technician's **backup notebook**:
* Before making permanent changes to official database files on disk, MySQL notes every change down in the Redo Log.
* If a power outage occurs before disk writing completes, MySQL inspects the notebook on startup:
  * **Committed transactions** are reapplied (Redo).
  * **Uncommitted transactions** are erased (Undo).

---

## ⚙️ Storage Engine Compatibility: InnoDB vs. MyISAM

Transactions work properly **ONLY** with transactional storage engines like **InnoDB**.

| Feature | `InnoDB` | `MyISAM` |
| :--- | :--- | :--- |
| **Transactions (`START TRANSACTION`)** | Supported ✅ | Not Supported ❌ |
| **Rollback (`ROLLBACK`)** | Undoes changes ✅ | Does nothing ❌ (Changes remain permanent) |
| **Crash Safety** | Crash-safe via Redo/Undo logs ✅ | Prone to corruption ❌ |
| **Default in MySQL** | Yes (MySQL 5.5+) ✅ | Legacy Engine ❌ |

> [!CAUTION]
> If you execute `ROLLBACK` on a `MyISAM` table, MySQL will throw a warning: `Warning 1196: Some non-transactional changed tables couldn't be rolled back`.

## 📈 Transaction State Transitions


During execution, a transaction transitions through several stages:

```
               ┌──────────────┐
               │    Active    │ <──────────┐
               └──────┬───────┘            │
                      │                    │
         ┌────────────┴────────────┐       │ (Begin)
         ▼                         ▼       │
 ┌──────────────┐          ┌──────────────┐│
 │Partially Comm│          │    Failed    ││
 └──────┬───────┘          └──────┬───────┘│
        │                         │        │
        ▼                         ▼        │
 ┌──────────────┐          ┌──────────────┐│
 │  Committed   │          │   Aborted    │┼
 └──────────────┘          └──────────────┘
   (Success!)             (Rollback Done)
```

1.  **Active**: The transaction starts and SQL queries are actively executing.
2.  **Partially Committed**: All SQL statements have finished executing, but the database has not yet written the updates permanently to the disk.
3.  **Committed**: The database writes the updates to the disk. The transaction succeeds.
4.  **Failed**: An error occurs during execution, or consistency constraints are violated.
5.  **Aborted**: The transaction is rolled back, removing all changes from memory, and the database returns to its pre-transaction state.
