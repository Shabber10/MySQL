# Day 08: Chapter 1 — ACID Properties & Transactions

In relational database systems, multiple SQL operations must often execute as a single, indivisible unit of work. This logical container is called a **Transaction**. If even one operation within the transaction fails, all preceding changes must be reversed, leaving the database in its original state.

To guarantee that your data remains safe, reliable, and correct, databases follow 4 fundamental rules called **ACID properties**.

---

## 🏫 The School Record Room Analogy
Imagine a database is like a school record room. It stores:
*   Student details 📋
*   Exam marks 📊
*   Fee receipts 💸
*   Attendance logs 📅

If something goes wrong while updating these records—for example, if a paper is lost or only half the details are written—the school can face serious administrative issues. To prevent this, databases enforce **ACID** properties.

---

## 🔒 The ACID Properties

ACID stands for:
*   **A** – Atomicity (All or Nothing)
*   **C** – Consistency (Data Stays Correct)
*   **I** – Isolation (No Interference)
*   **D** – Durability (Saved Permanently)

Let's explore each of these properties in detail with real-life and database examples.

---

### 1. Atomicity ("All or Nothing")

#### 🎬 Real-Life Example: Buying a Movie Ticket
Suppose you are booking a movie ticket online. The system must perform two critical steps:
1.  **Step 1:** Deduct ₹250 from your bank account.
2.  **Step 2:** Book the movie seat.

*   **Situation 1 (Success):** Money is deducted ✅ and the seat is booked ✅. Everything is fine.
*   **Situation 2 (Failure):** Money is deducted ✅ but the seat booking fails ❌. If the system stopped here, you would lose ₹250 without getting a ticket!
*   **Correct Behavior (Atomicity):** If the seat booking fails, the system must return your ₹250 (roll back). Either both steps succeed, or both steps fail: Money deducted ❌ and Seat booked ❌ (returns to previous state).

#### 🛠 Other Real-Life Examples:
*   **ATM Cash Withdrawal:** Your bank account balance is only updated if cash actually comes out of the machine. If the ATM fails to dispense cash, the transaction is cancelled and your money is not debited.
*   **Food Delivery:** Payment is successful, restaurant accepts, and delivery starts. If the restaurant rejects the order, the payment is refunded.

#### 💻 Database Example:
Suppose you are running two SQL queries inside a single transaction to transfer money:
```sql
-- Step 1: Remove ₹1000 from Account 1
UPDATE accounts 
SET balance = balance - 1000 
WHERE id = 1;

-- Step 2: Add ₹1000 to Account 2
UPDATE accounts 
SET balance = balance + 1000 
WHERE id = 2;
```
If the second query fails (e.g., due to database crash or constraint violation), the database engine automatically cancels the first query using a **Rollback** operation. No money disappears.

---

### 2. Consistency ("Data Should Always Be Correct")

Consistency ensures the database always transitions from one valid state to another, complying with all constraints, rules, and business logic.

#### 🏫 Real-Life Example: Classroom Total
A teacher maintains a classroom record sheet:
*   Boys = 20
*   Girls = 20
*   **Total = 40** (This is correct, as $20 + 20 = 40$)

If someone modifies the record incorrectly to:
*   Boys = 25
*   Girls = 20
*   **Total = 40**

This represents **inconsistent** data ($25 + 20 \neq 40$). A consistent database never allows these rules or totals to mismatch.

#### 🏦 Bank Example:
Before a transfer, your accounts have:
*   Your Account = ₹5000
*   Friend's Account = ₹3000
*   **Total Money in System = ₹8000**

You transfer ₹1000. Under consistency rules:
*   Your Account = ₹4000
*   Friend's Account = ₹4000
*   **Total Money in System = ₹8000** (No money is lost or created)

If the database allowed your account to become ₹4000 while leaving your friend's account at ₹3000 (Total = ₹7000), consistency would be broken. MySQL prevents this.

#### 🔑 Database Constraints Example:
If you have a database table for students where `student_id` is a `PRIMARY KEY` (Unique):
*   Already existing: `101 Rahul`, `102 Priya`
*   If you attempt to insert `101 Ramesh`, the database rejects it with an error. The database rules (constraints) cannot be broken, preserving consistency.

---

### 3. Isolation ("No Interference Between Users")

Isolation guarantees that concurrently executing transactions do not interfere with each other. The intermediate state of a transaction remains invisible to other transactions.

#### 🏧 Real-Life Example: Simultaneous ATM Withdrawals
You have ₹10,000 in your account.
1.  **You** start withdrawing ₹5000 at ATM A.
2.  At the exact same time, your **brother** tries to withdraw ₹7000 at ATM B.
3.  Both requests hit the bank server simultaneously.

Without isolation, both ATM machines might read the same initial balance of ₹10,000. ATM A dispenses ₹5,000, and ATM B dispenses ₹7,000. You have successfully withdrawn ₹12,000 from a ₹10,000 account—which is impossible!

Isolation ensures the database finishes processing one transaction before starting another, or uses concurrency locks to prevent them from reading uncommitted, intermediate states.

#### 📄 Word Document Example:
If two people edit the same line of a shared document at the exact same time without isolation control, their sentences mix and create garbled text. Isolation avoids this conflict by locking the resource or separating versions.

---

### 4. Durability ("Saved Permanently")

Durability ensures that once a transaction is successfully completed (committed), its changes are recorded in permanent storage (disk) and cannot be lost, even in the event of a system crash, power outage, or hardware failure.

#### 📝 Real-Life Example: Exam Paper Collection
You are writing an exam. Once you finish, the teacher collects your paper and stores it in the file locker. If the electricity goes off immediately after, your paper does not disappear; it is safely stored.

#### 💾 Software Example:
You are working on a Word file. You press **Ctrl + S** to save it. If the computer suddenly shuts down, your work is still there when you reboot because it was written to the disk.

#### 🏦 Bank Example:
You successfully transfer ₹5000 and receive a "Transaction Successful" confirmation. Immediately after, the bank's servers crash. When they restart, the database recovers and the transfer records remain intact.

---

## 🍕 The Complete Story: Pizza Analogy

Let's look at one final analogy that encapsulates all four properties: **Ordering a Pizza Online** 🍕

*   **Atomicity:** Either the payment is deducted and the pizza order is placed, or neither happens. If your payment succeeds but the restaurant rejects the order, your money is refunded.
*   **Consistency:** The price of the pizza, delivery charges, and taxes must always sum up to the total amount paid. Your wallet balance before and after the purchase remains mathematically consistent.
*   **Isolation:** Your order status and payment checkout process do not interfere with another customer ordering a pizza at the same time.
*   **Durability:** Once your order is confirmed and the app says "Out for Delivery", that confirmation is saved. Even if your phone battery dies, the delivery driver still shows up because the order is saved permanently on the restaurant's servers.

## 🔄 Does Every Transaction Follow ACID Properties?

**Yes**, a database transaction is expected to satisfy all ACID properties. However, in **MySQL**, these guarantees depend on the **Storage Engine** you choose:

*   ✅ **InnoDB:** MySQL's default storage engine. It is **fully transactional** and provides complete ACID guarantees.
*   ❌ **MyISAM:** An older storage engine. It is **non-transactional** and does **not** support transaction control statements (`ROLLBACK` has no effect on MyISAM tables) or full ACID guarantees.

---

## ⚙️ Under the Hood: What Happens When You Run `START TRANSACTION;`?

When you execute `START TRANSACTION;` (or `BEGIN;`), MySQL performs three main operations internally:

1.  **Disables Auto-Commit Mode:** By default, MySQL operates with `autocommit = ON` (each SQL statement is committed immediately). `START TRANSACTION;` turns this off for the session. Changes are temporary until you run `COMMIT;`.
2.  **Begins a Safe Transaction Block:** All subsequent DML operations (INSERT, UPDATE, DELETE) are grouped together.
3.  **Prepares Transaction Logging:** MySQL initializes transaction logs to keep track of changes in memory before saving them to disk.

---

## 📝 Transaction Logs: Redo and Undo Logs

MySQL doesn't write changes directly to database tables on disk immediately. Instead, to maximize speed while ensuring safety, it uses memory buffers and **transaction logs**:

### 1. The Redo Log (Ensures Durability)
*   **Role:** Records changes about to be made to the data. 
*   **Engine:** Managed by the InnoDB storage engine.
*   **How it works:** When a transaction is committed, InnoDB writes the changes to the Redo Log on disk first. Writing to logs is extremely fast compared to updating the entire database table files.
*   **Crash Recovery:** If the server suddenly crashes, MySQL checks the Redo Log on startup to reapply (redo) changes from any committed transactions that weren't fully written to the table files yet.

### 2. The Undo Log (Ensures Atomicity & Isolation)
*   **Role:** Stores the "before image" of the data (the old values before they were modified).
*   **How it works:** If you issue a `ROLLBACK`, MySQL reads the Undo Log to revert the modified rows back to their original state. It is also used to provide consistent reads for other sessions (Isolation).

### 📓 The "Backup Notebook" Analogy
Think of the **Redo Log** as a **"backup notebook"** where you write down every change you intend to make before writing it into the main ledger. 
*   If the power goes out before you update the main ledger, you open your notebook on restart, see the written changes, and **reapply them**.
*   If you decide to cancel your changes midway, you look at your notes of what was there before (the **Undo Log**) and restore the original values.

```
                  ┌──────────────────────────────┐
                  │      START TRANSACTION;      │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
         ┌───────────────────────────────────────────────┐
         │ DML Statements (INSERT, UPDATE, DELETE)       │
         │ - Old values stored in UNDO LOG               │
         │ - New values stored in REDO LOG Buffer        │
         └───────────────────────┬───────────────────────┘
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
         ┌───────────────┐               ┌───────────────┐
         │    COMMIT;    │               │   ROLLBACK;   │
         └───────┬───────┘               └───────┬───────┘
                 │                               │
                 ▼                               ▼
       REDO LOG written to disk           UNDO LOG applied
       (Changes permanent ✅)              (Changes reversed ❌)
```

### 🧩 Step-by-Step Logging & Crash Recovery Flow

1.  **Start Transaction:** When `START TRANSACTION;` is executed, the redo log begins recording memory changes.
2.  **Change Data:** As statements execute, the old data values are saved in the **Undo Log** (in case of a rollback) and the new values are written to the **Redo Log Buffer** in memory.
3.  **Commit:** When `COMMIT;` is run, the redo log buffer is flushed and written permanently to the **Redo Log** on disk. This ensures durability.
4.  **Rollback:** If `ROLLBACK;` is run instead, MySQL reads the before-images from the **Undo Log** and restores the data to its original state.
5.  **Crash Recovery:** If the database crashes:
    *   **Uncommitted Transactions:** MySQL scans the logs on restart. If a transaction has no commit record, MySQL uses the **Undo Log** to roll it back automatically.
    *   **Committed but Unwritten Transactions:** If a transaction was committed but the changes were not yet moved from memory buffer to the final database files, MySQL uses the **Redo Log** to reapply the updates.
