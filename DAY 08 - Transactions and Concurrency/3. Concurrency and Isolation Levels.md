# Day 08: Chapter 3 — Concurrency & Isolation Levels

When multiple users query and write to the same database simultaneously, we must control how their transactions overlap. Relational databases manage this concurrency using **Isolation Levels** and **Locks**.

---

## 1. Concurrency Read Phenomena

Without proper isolation, concurrent transactions can experience three classic read problems:

### A. Dirty Read
Transaction A reads data modified by Transaction B **before** Transaction B commits. If Transaction B rolls back, Transaction A has read invalid data that "never existed".
*   *Scenario:* Transaction B debits $100. Transaction A reads the balance. Transaction B rolls back. Transaction A is working with the wrong balance.

### B. Non-repeatable Read
Transaction A reads a row once. Then, Transaction B updates that same row and commits. When Transaction A reads the row again in the same transaction, it finds **different values**.
*   *Scenario:* Transaction A reads a product price as $50. Transaction B updates the price to $45 and commits. Transaction A re-reads the price and finds it is now $45.

### C. Phantom Read
Transaction A queries a range of rows matching a search criteria. Transaction B inserts or deletes a row within that range and commits. When Transaction A runs the range query again, **new rows ("phantoms")** appear, or existing rows disappear.
*   *Scenario:* Transaction A counts employees in department 'IT' and finds 5. Transaction B inserts a new 'IT' employee and commits. Transaction A counts again and finds 6.

---

## 2. Standard Transaction Isolation Levels

The SQL standard defines four isolation levels. Higher isolation levels prevent more read phenomena but reduce performance by forcing transactions to wait for locks.

| Isolation Level | Dirty Reads | Non-repeatable Reads | Phantom Reads | Performance |
| :--- | :--- | :--- | :--- | :--- |
| **`READ UNCOMMITTED`** | Allowed ❌ | Allowed ❌ | Allowed ❌ | Extremely Fast |
| **`READ COMMITTED`** | Prevented ✔ | Allowed ❌ | Allowed ❌ | Balanced |
| **`REPEATABLE READ`** | Prevented ✔ | Prevented ✔ | Prevented (in MySQL) | High |
| **`SERIALIZABLE`** | Prevented ✔ | Prevented ✔ | Prevented ✔ | Very Slow |

> [!TIP]
> **MySQL Default:** MySQL defaults to **`REPEATABLE READ`**. Unlike many other databases, MySQL's InnoDB storage engine prevents both Non-repeatable Reads and Phantom Reads at the `REPEATABLE READ` level using a mechanism called **Next-Key Locking** (locking index ranges).

### Changing Isolation Levels in MySQL

*   **For the next transaction only:**
    ```sql
    SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
    ```
*   **For the current session connection:**
    ```sql
    SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
    ```
*   **Globally for all new connections:**
    ```sql
    SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;
    ```

## 3. Row-Level Locks in MySQL

To enforce isolation levels, MySQL locks records during execution. You can manually request locks on rows within a transaction to prevent concurrent updates:

### A. Shared Lock (S-Lock): `FOR SHARE`
Allows other transactions to read the locked rows, but **prevents them from modifying** the rows until your transaction commits.
```sql
START TRANSACTION;
SELECT * FROM Accounts WHERE id = 1 FOR SHARE; -- Locks row 1 for reading
-- Other sessions can run SELECT, but UPDATE statements on row 1 will hang in a queue.
COMMIT; -- Releases lock
```
*(Note: `LOCK IN SHARE MODE` is the older MySQL syntax, replaced by `FOR SHARE` in MySQL 8.0).*

### B. Exclusive Lock (X-Lock): `FOR UPDATE`
Prevents other transactions from modifying the rows, and prevents them from reading the rows using `FOR SHARE` or `FOR UPDATE`.
```sql
START TRANSACTION;
SELECT * FROM Accounts WHERE id = 1 FOR UPDATE; -- Locks row 1 for writing
-- Other sessions' SELECT ... FOR SHARE / FOR UPDATE / UPDATE queries on row 1 will block.
COMMIT; -- Releases lock
```
