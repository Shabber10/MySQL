# Day 06: Chapter 2 — Database Normalization (1NF, 2NF, 3NF)

**Database Normalization** is a systematic process of organizing database schemas to minimize data redundancy, eliminate data anomalies, and ensure data integrity. It involves dividing a large, unorganized table into smaller, well-structured related tables.

---

## 🧹 Real-Life Analogy: Organizing a Cupboard 🚪

Imagine your bedroom cupboard:
*   **Without Arrangement (Unnormalized):** Books, clothes, shoes, files, and laptop are all mixed together in one pile. Finding anything takes forever, and items get damaged.
*   **After Arrangement (Normalized):** 
    *   Books Shelf 📚
    *   Clothes Shelf 👕
    *   Shoes Shelf 👟
    *   Documents Shelf 📁

Everything is organized, easy to find, and simple to maintain. Normalization does exactly this for database tables!

---

## ⚠️ Why Normalization? The 4 Database Anomalies

Consider an unnormalized college table storing student, department, and course details in a single table:

| Student_ID | Student_Name | Department | HOD | Course1 | Course2 | Course3 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 101 | Rahul | CSE | Ramesh | DBMS | Java | Python |
| 102 | Priya | CSE | Ramesh | DBMS | Java | Python |
| 103 | Kiran | ECE | Suresh | Networks | Signals | VLSI |

Storing everything in one table creates four major problems:

### 1. Data Redundancy (Duplicate Data)
The department name `CSE` and HOD name `Ramesh` are repeated for every CSE student. In a college with 1,000 CSE students, `Ramesh` is stored 1,000 times, wasting disk space.

### 2. Update Anomaly
If the CSE department HOD changes from **Ramesh** to **Mahesh**, you must update hundreds of student records. If you miss even one row, the database displays conflicting HOD names for the same department.

### 3. Insertion Anomaly
Suppose the college opens a new **AI Department** with HOD **Sunil**, but no students have enrolled yet. You cannot insert the new department into the table because `Student_ID` (the primary key) cannot be `NULL`.

### 4. Deletion Anomaly
If student **Kiran** leaves the college and you delete his row, the entire **ECE Department** information (and HOD **Suresh**) is completely wiped out from the database!

## 🪜 The Normalization Path

Normal forms are progressive: a table must satisfy 1NF before 2NF, and 2NF before 3NF.

```
   ┌────────────────────────────────────────────────────────┐
   │                  UNNORMALIZED TABLE                    │
   └───────────┬────────────────────────────────────────────┘
               │  Rule: Make all cells atomic (single values)
               ▼
   ┌────────────────────────────────────────────────────────┐
   │                 1st NORMAL FORM (1NF)                  │
   └───────────┬────────────────────────────────────────────┘
               │  Rule: Remove partial dependencies
               ▼
   ┌────────────────────────────────────────────────────────┐
   │                 2nd NORMAL FORM (2NF)                  │
   └───────────┬────────────────────────────────────────────┘
               │  Rule: Remove transitive dependencies
               ▼
   ┌────────────────────────────────────────────────────────┐
   │                 3rd NORMAL FORM (3NF)                  │
   └────────────────────────────────────────────────────────┘
```

---

## 1️⃣ 1st Normal Form (1NF): Atomic Values

A table is in **1st Normal Form** if:
1. Every cell contains a **single, atomic (indivisible) value**.
2. There are **no repeating groups** or comma-separated lists in a single cell.
3. Each row is unique, identified by a defined Primary Key.

### ❌ Unnormalized Example (Multi-Valued Cells):
| RollNo | SName | Branch | Languages |
| :--- | :--- | :--- | :--- |
| 101 | Alice | CSE | Java, Python |
| 102 | Bob | ECE | C, C++ |
| 103 | Charlie | CSE | Java, C, Python |

*Problem:* The `Languages` column holds multiple values in a single cell.

### ✅ 1NF Decomposed Table:
Break multi-valued cells into individual rows.

| RollNo (PK) | SName | Branch | Language (PK) |
| :--- | :--- | :--- | :--- |
| **101** | Alice | CSE | **Java** |
| **101** | Alice | CSE | **Python** |
| **102** | Bob | ECE | **C** |
| **102** | Bob | ECE | **C++** |
| **103** | Charlie | CSE | **Java** |
| **103** | Charlie | CSE | **C** |
| **103** | Charlie | CSE | **Python** |

🎯 **Easy Rule for 1NF:** *"One Cell = One Value"*

---

## 2️⃣ 2nd Normal Form (2NF): No Partial Dependency

A table is in **2nd Normal Form** if:
1. It is already in **1NF**.
2. Every non-key column depends on the **entire primary key**, not just part of it.

> **What is a Partial Dependency?**
> Occurs when a non-key attribute depends on only *part* of a composite primary key `{RollNo, Language}`. 
> *(Note: If a table has a single-column primary key, it is automatically in 2NF!)*

### ❌ 1NF Table with Partial Dependency:
In the table above with composite key `{RollNo, Language}`:
* `Language` depends on `{RollNo, Language}`.
* `SName` and `Branch` depend **only** on `RollNo`, NOT on `Language` (Partial Dependency ❌).

### ✅ 2NF Decomposed Tables:
Split into two tables to eliminate partial dependencies:

#### 1. `Students` Table (PK: `RollNo`)
| RollNo | SName | Branch |
| :--- | :--- | :--- |
| 101 | Alice | CSE |
| 102 | Bob | ECE |
| 103 | Charlie | CSE |

#### 2. `Student_Languages` Table (Composite PK: `{RollNo, Language}`)
| RollNo | Language |
| :--- | :--- |
| 101 | Java |
| 101 | Python |
| 102 | C |
| 102 | C++ |
| 103 | Java |
| 103 | C |
| 103 | Python |

🎯 **Easy Rule for 2NF:** *"Depend on the Whole Primary Key"*

---

## 3️⃣ 3rd Normal Form (3NF): No Transitive Dependency

A table is in **3rd Normal Form** if:
1. It is already in **2NF**.
2. No non-key column depends on another non-key column (**No Transitive Dependency**).

> **What is a Transitive Dependency?**
> A non-key column depends on another non-key column, which in turn depends on the primary key ($A \rightarrow B \rightarrow C$). Attributes must depend *only* on the primary key.

### ❌ 2NF Table with Transitive Dependency:
Consider the `Students` table (PK: `RollNo`):

| RollNo (PK) | SName | Branch | HODName |
| :--- | :--- | :--- | :--- |
| 101 | Alice | CSE | Dr. Rao |
| 102 | Bob | ECE | Dr. Mehta |
| 103 | Charlie | CSE | Dr. Rao |

*   `RollNo` $\rightarrow$ `Branch` (Primary Key determines Branch).
*   `Branch` $\rightarrow$ `HODName` (`HODName` is determined by `Branch`, which is a non-key column ❌).
*   Therefore, `RollNo` $\rightarrow$ `Branch` $\rightarrow$ `HODName` is a **transitive dependency**.

### ✅ 3NF Decomposed Tables:
Split into separate entity tables to eliminate transitive dependencies:

#### 1. `Student` Table (PK: `RollNo`, FK: `Branch`)
| RollNo | SName | Branch |
| :--- | :--- | :--- |
| 101 | Alice | CSE |
| 102 | Bob | ECE |
| 103 | Charlie | CSE |

#### 2. `Branch` Table (PK: `Branch`)
| Branch | HODName |
| :--- | :--- |
| CSE | Dr. Rao |
| ECE | Dr. Mehta |

#### 3. `Student_Languages` Table (Composite PK: `{RollNo, Language}`)
| RollNo | Language |
| :--- | :--- |
| 101 | Java |
| 101 | Python |

🎯 **Easy Rule for 3NF:** *"Depend Only on the Primary Key"*

---

## 📊 Summary Comparison: 1NF vs 2NF vs 3NF

| Feature | 1NF 1️⃣ | 2NF 2️⃣ | 3NF 3️⃣ |
| :--- | :--- | :--- | :--- |
| **Main Goal** | Ensure atomic values in cells | Eliminate partial dependencies | Eliminate transitive dependencies |
| **Prerequisite** | Table structure | Must be in 1NF | Must be in 2NF |
| **Removes** | Multi-valued attributes & repeating groups | Redundancy from composite key parts | Redundancy from non-key attribute dependencies |
| **Focus** | Single value per cell | Non-key depends on *all* parts of PK | Non-key depends *only* on PK |
| **Mnemonic** | *"One Cell = One Value"* | *"The Whole Key"* | *"Nothing But The Key"* |

## ⚖️ Advantages and Disadvantages of Normalization

### ✅ Advantages:
1. **Eliminates Redundancy:** Avoids duplicate data, drastically reducing storage space.
2. **Prevents Anomalies:** Eliminates Insertion, Deletion, and Update anomalies.
3. **Improves Data Integrity:** Changes (e.g. updating HOD name) happen in one single row instead of hundreds.
4. **Clean Architecture:** Organized schema with well-defined entity relationships.

### ❌ Disadvantages (The Trade-Off):
1. **Increased Complexity:** Splitting tables creates more tables to manage.
2. **Query Performance Overhead:** Joining multiple tables (`JOIN`) can slow down read-heavy reporting queries.
3. **Complex Queries:** Writing queries requires joining multiple tables rather than scanning a single flat file.

> 💡 **Real-World Engineering Balance:**
> OLTP (Online Transaction Processing) systems use **High Normalization (3NF/BCNF)** for fast, safe writes. Data Warehouses (OLAP) often use **Denormalization** for fast analytical read queries.
