# Day 06: Chapter 2 — Database Normalization (1NF, 2NF, 3NF)

**Database Normalization** is a systematic process of organizing database schemas to minimize data redundancy and prevent data anomalies. It involves breaking a large, bloated table into smaller, well-structured tables and defining relationships between them.

---

## ⚠️ The Three Database Anomalies

An unnormalized table stores unrelated information in a single row. This causes three major types of problems:

### 1. Insertion Anomaly
You cannot insert certain facts because they require other, unrelated facts that are not yet available.
*   *Example:* If a table stores both Employee and Department details, you cannot add a new department to the database until you hire at least one employee to work in it (because the primary key is `emp_id`).

### 2. Update (Modification) Anomaly
When redundant data is updated, you must modify multiple rows. If even one row is missed, it leads to inconsistent data.
*   *Example:* If a department's office location is stored in every employee's row, moving that department's office requires updating hundreds of employee records. If a few records fail to update, the database displays conflicting locations.

### 3. Deletion Anomaly
Deleting a record accidentally destroys unrelated information that you wanted to keep.
*   *Example:* If a department's details are stored only in its employees' rows, deleting the last employee in the department deletes the entire department's existence and office location from the system.

---

## 🪜 The Normalization Path

Normal forms are progressive: a table must satisfy the rules of $1\text{NF}$ to qualify for $2\text{NF}$, and must be in $2\text{NF}$ to qualify for $3\text{NF}$.

```
   ┌────────────────────────────────────────────────────────┐
   │                       UNNORMALIZED                     │
   └───────────┬────────────────────────────────────────────┘
               │  Rule: Make all cells atomic
               ▼
   ┌────────────────────────────────────────────────────────┐
   │                   1st NORMAL FORM (1NF)                │
   └───────────┬────────────────────────────────────────────┘
               │  Rule: Remove partial dependencies
               ▼
   ┌────────────────────────────────────────────────────────┐
   │                   2nd NORMAL FORM (2NF)                │
   └───────────┬────────────────────────────────────────────┘
               │  Rule: Remove transitive dependencies
               ▼
   ┌────────────────────────────────────────────────────────┐
   │                   3rd NORMAL FORM (1NF)                │
   └────────────────────────────────────────────────────────┘
```

---

## 1️⃣ 1st Normal Form (1NF): Atomicity

A table is in **1st Normal Form** if and only if:
1.  Every cell contains a **single, atomic (indivisible) value**. (No comma-separated lists, nested tables, or array values).
2.  Columns contain only values of the same domain/data type.
3.  Each row is unique, identified by a defined **Primary Key**.

### Example: Unnormalized Table
Here, the `skills` column contains multiple values, which violates 1NF:

| emp_id | emp_name | dept | skills |
| :--- | :--- | :--- | :--- |
| 101 | Amit | IT | SQL, Java |
| 102 | Sara | HR | Recruiting |

### Decomposed 1NF Table
We split the multi-valued cells into separate rows. The primary key becomes a composite key: `{emp_id, skill}`.

| emp_id | emp_name | dept | skill |
| :--- | :--- | :--- | :--- |
| **101** | Amit | IT | **SQL** |
| **101** | Amit | IT | **Java** |
| **102** | Sara | HR | **Recruiting** |

---

## 2️⃣ 2nd Normal Form (2NF): Full Functional Dependency

A table is in **2nd Normal Form** if:
1.  It is already in **1NF**.
2.  It has **no partial dependencies**. 

> **What is a Partial Dependency?**
> A partial dependency occurs when a non-key column depends on only **part** of a composite primary key. If your table has a single-column primary key, it is automatically in 2NF!

### Example: 1NF Table with Partial Dependency
Consider an assignments table where the composite primary key is `{emp_id, project_id}`:

| emp_id (PK) | project_id (PK) | emp_name | project_name | hours_worked |
| :--- | :--- | :--- | :--- | :--- |
| 101 | P1 | Amit | Phoenix | 20 |
| 101 | P2 | Amit | Apollo | 15 |
| 102 | P1 | Sara | Phoenix | 35 |

*   **Identified Dependencies:**
    - `hours_worked` depends on `{emp_id, project_id}` (Full dependency).
    - `emp_name` depends **only** on `emp_id` (Partial dependency ❌).
    - `project_name` depends **only** on `project_id` (Partial dependency ❌).

### Decomposed 2NF Tables
We remove the partial dependencies by splitting them into three separate tables:

#### 1. `Employees` Table (PK: `emp_id`)
| emp_id | emp_name |
| :--- | :--- |
| 101 | Amit |
| 102 | Sara |

#### 2. `Projects` Table (PK: `project_id`)
| project_id | project_name |
| :--- | :--- |
| P1 | Phoenix |
| P2 | Apollo |

#### 3. `Assignments` Table (Composite PK: `{emp_id, project_id}`)
| emp_id | project_id | hours_worked |
| :--- | :--- | :--- |
| 101 | P1 | 20 |
| 101 | P2 | 15 |
| 102 | P1 | 35 |

---

## 3️⃣ 3rd Normal Form (3NF): Non-Transitive Dependency

A table is in **3rd Normal Form** if:
1.  It is in **2NF**.
2.  It has **no transitive dependencies**.

> **What is a Transitive Dependency?**
> A transitive dependency occurs when a non-key column depends on another non-key column, which in turn depends on the primary key ($A \rightarrow B \rightarrow C$). All attributes must depend only on the primary key (or as the mnemonic goes: "the key, the whole key, and nothing but the key, so help me Codd").

### Example: 2NF Table with Transitive Dependency
Consider this employees table (PK: `emp_id`):

| emp_id (PK) | emp_name | dept_id | dept_name | office_location |
| :--- | :--- | :--- | :--- | :--- |
| 101 | Amit | D10 | IT | Floor 4 |
| 102 | Sara | D20 | HR | Floor 1 |
| 103 | John | D10 | IT | Floor 4 |

*   **Identified Dependencies:**
    - `dept_id` depends on `emp_id` ($emp\_id \rightarrow dept\_id$).
    - `dept_name` and `office_location` depend on `dept_id` ($dept\_id \rightarrow dept\_name$).
    - Therefore, `dept_name` depends transitively on `emp_id` via `dept_id` ($emp\_id \rightarrow dept\_id \rightarrow dept\_name$ ❌).

### Decomposed 3NF Tables
We extract the department details into a separate table to break the transitive dependency:

#### 1. `Employees` Table (PK: `emp_id`, FK: `dept_id`)
| emp_id | emp_name | dept_id |
| :--- | :--- | :--- |
| 101 | Amit | D10 |
| 102 | Sara | D20 |
| 103 | John | D10 |

#### 2. `Departments` Table (PK: `dept_id`)
| dept_id | dept_name | office_location |
| :--- | :--- | :--- |
| D10 | IT | Floor 4 |
| D20 | HR | Floor 1 |
