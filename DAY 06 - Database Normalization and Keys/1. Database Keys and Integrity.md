# Day 06: Chapter 1 — Database Keys & Integrity

In relational database design, records must be uniquely identifiable, and the relationships between tables must remain reliable. **Database Keys** are columns or groups of columns that uniquely identify rows and establish relationships. **Integrity Constraints** enforce rules to prevent invalid data from corrupting the database.

---

## 1. Types of Database Keys

```
               ┌──────────────────────────────────────────────────┐
               │                  SUPER KEY                       │
               │   (Any combination that uniquely identifies a row)│
               │   e.g., {emp_id}, {emp_id, email}, {emp_id, dept} │
               │   ┌──────────────────────────────────────────┐   │
               │   │             CANDIDATE KEY                │   │
               │   │   (Minimal super key with no redundants) │   │
               │   │   e.g., {emp_id}, {email}                │   │
               │   │   ┌──────────────┐                       │   │
               │   │   │ PRIMARY KEY  │                       │   │
               │   │   │  (Chosen CK) │                       │   │
               │   │   └──────────────┘                       │   │
               │   └──────────────────────────────────────────┘   │
               └──────────────────────────────────────────────────┘
```

### A. Super Key
A **Super Key** is any column or set of columns that uniquely identifies a row within a table. A table can have many super keys, and they can contain redundant (extra) columns.
*   *Example:* If `emp_id` is unique, then `{emp_id}`, `{emp_id, name}`, and `{emp_id, email, dept}` are all super keys.

### B. Candidate Key
A **Candidate Key** is a minimal Super Key. It is a set of columns that uniquely identifies a row, but if you remove any column from the set, it loses its uniqueness.
*   *Example:* If both `emp_id` and `email` are unique on their own, they are both candidate keys (neither contains redundant columns). `{emp_id, name}` is a super key but *not* a candidate key, because `name` is redundant for uniqueness.

### C. Primary Key (PK)
A **Primary Key** is the candidate key selected by the database designer to uniquely identify rows in the table. 
*   **Rules:**
    1.  Only **one** Primary Key is allowed per table.
    2.  It **cannot** contain `NULL` values.
    3.  Its value must be unique across all rows.

### D. Unique Key (UK)
A **Unique Key** (or Unique Constraint) ensures that all values in a column or set of columns are distinct.
*   **Differences from Primary Key:**
    - A table can have **multiple** Unique Keys.
    - Unique columns **allow `NULL` values** (in MySQL, multiple rows can contain `NULL` under a unique constraint, because `NULL` represents an unknown value, and one unknown is not considered equal to another).

### E. Composite Key
A **Composite Key** is a primary key or unique key that consists of **two or more columns**. It is used when a single column is insufficient to uniquely identify a row.
*   *Example:* In an `Enrollments` table linking students and courses, neither `student_id` nor `course_id` is unique alone. Together, `{student_id, course_id}` forms a unique composite primary key.

### F. Foreign Key (FK)
A **Foreign Key** is a column (or group of columns) in one table that points to the Primary Key (or Unique Key) of another table. It is used to link tables together and enforce relationships.
*   The table containing the foreign key is the **child table**.
*   The table containing the referenced key is the **parent table**.

---

## ⚖️ Comparison: Primary Key vs. Unique Key

| Feature | Primary Key (PK) | Unique Key (UK) |
| :--- | :--- | :--- |
| **Limit per Table** | Exactly **one** per table. | **Multiple** unique keys allowed. |
| **Nullability** | Strictly `NOT NULL`. | Allows `NULL` values (MySQL allows multiple `NULL`s). |
| **Indexes** | Automatically creates a **Clustered Index**. | Automatically creates a **Non-clustered Index**. |
| **Purpose** | Uniquely identifies a record. | Prevents duplicates in secondary columns. |

## 🔒 Data Integrity Constraints

Data integrity ensures that the information stored in a database is accurate, complete, and reliable. There are two critical integrity rules enforced by keys:

### 1. Entity Integrity (Row-Level Constraints)
**Entity Integrity** states that every table must have a primary key, and the primary key column(s) **must not contain NULL values** or duplicates.
*   *Why?* If a primary key could be `NULL`, we would have a record that cannot be identified or linked.
*   *Enforced by:* Creating a `PRIMARY KEY` constraint.

### 2. Referential Integrity (Relationship-Level Constraints)
**Referential Integrity** states that a Foreign Key in a child table must always point to a **valid, existing** Primary Key in the parent table, or be completely `NULL`.
*   *Why?* This prevents "orphaned" records (e.g., an order referencing a customer ID that does not exist).
*   *Enforced by:* Creating a `FOREIGN KEY` constraint.

#### Referential Actions (On Parent Delete/Update)
When a referenced row in the parent table is deleted or updated, what happens to the child rows? MySQL allows you to define this behavior:
1.  **`ON DELETE RESTRICT` / `NO ACTION`** (Default): Prevents the parent row from being deleted if child rows reference it.
2.  **`ON DELETE CASCADE`**: Automatically deletes/updates child rows when the parent row is deleted/updated.
3.  **`ON DELETE SET NULL`**: Sets the foreign key column in the child rows to `NULL` when the parent row is deleted.
